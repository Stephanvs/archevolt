The measured warmed, fixed-capacity updates allocate zero managed bytes, with one worker or four. This page lists measured times for common operations on one machine. The [2 November benchmark checkpoint](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/results.md) contains every case available at that commit, the Bevy 0.20.0 counterparts, the per-class BenchmarkDotNet tables, and the reruns of noisy cases.

:::note
The numbers come from one machine and one run of the suite. They are not a regression limit, and they do not rank Archevolt against another ECS.
:::

Unless a section says otherwise, every table was measured on 2 November 2026, at commit `8029e7f`, on an AMD Ryzen 9 5950X with Windows 11 Pro, .NET 11.0.0-rc.3, a Release build, and BenchmarkDotNet 0.16.0-preview.2 with its default job. The machine was otherwise idle. Each value is the median of three process runs in microseconds, with the fastest and slowest run in brackets.

That source tree matches release `v0.5.5`. Later code runs single-work-item batches on the owner thread without waking idle workers. The [4 November dispatch and partitioning study](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/query-partition-threshold.md) measures that change separately. The tables here retain the earlier checkpoint and do not measure the updated dispatch path. Later still, worker threads spin briefly between batches instead of blocking at once. The [5 November report](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/performance-hill-climb-report.md) measures that change. Its [second round](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/performance-hill-climb-round-2.md) measures `[Each]` methods compiled into [SIMD kernels](/guides/systems#simd-kernels). Three rows on this page carry that round's values instead of the checkpoint's: the `[Each]` row under [Dense movement at 100,000 entities](#dense-movement-at-100000-entities) and the two write rows under [Change filters](#change-filters). That round ran on 5 November 2026 on the same machine while it was in normal use, so those ranges are wider. The [10 November report](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/each-kernels.md) measures kernels for methods with branches and helper calls, and a faster loop for methods that are not kernels. [`[Each]` methods by shape](#each-methods-by-shape) has its numbers. The [11 November report](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/system-overhead.md) measures what a schedule pays to run a system before the system visits an entity. [What a system costs before it does work](#what-a-system-costs-before-it-does-work) has its numbers.

## Dense movement at 100,000 entities

All cases use the same `Position` and `Velocity` structs, initial values, and per-row arithmetic, with untracked components. The `Vector256` case writes that arithmetic with explicit SIMD. The handwritten loop has no scheduler. Archevolt's numbers include schedule dispatch, resource access, lease checks, and query traversal. The generator compiles the `[Each]` method into a [SIMD kernel](/guides/systems#simd-kernels), which is why it measures close to the `Vector256` case.

| Case | Median µs [range] | ns per entity |
| --- | ---: | ---: |
| Handwritten loop | 83.06 [82.94, 83.41] | 0.831 |
| Generated `[Each]` | 22.04 [21.64, 40.03] | 0.220 |
| Generated `[EachBlock]`, indexed loop | 83.06 [82.99, 83.17] | 0.831 |
| Generated `[EachBlock]`, `Vector256` | 20.96 [20.91, 21.07] | 0.210 |
| Named query, `foreach` over rows | 83.16 [82.48, 84.21] | 0.832 |

The `[Each]` row is from 5 November 2026. Another batch that day measured 21.41 [20.94, 22.16].

A named query's time depends on how the JIT lays out its loop in each process. Over the [traversal matrix](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/results.md#traversal-matrix), the same 100,000-entity named query measured about 82 µs in some processes and about 94 µs in others.

## `[Each]` methods by shape

How an `[Each]` method is written decides whether it runs as a [SIMD kernel](/guides/systems#simd-kernels). These cases were measured on 10 November 2026 on a different machine from the other tables: an AMD Ryzen AI 9 HX 370 running Linux, with the process pinned to two cores, .NET 11.0.0-rc.3, one worker, and 100,000 entities. Each value is the median of five process runs. The [report](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/each-kernels.md) has the ranges, a second machine, and NativeAOT.

| Method | Runs as | ns per entity |
| --- | --- | ---: |
| Moves a position by a velocity | Kernel | 0.114 |
| Moves a position and wraps it with `if` | Kernel | 0.113 |
| Wraps through a helper method | Kernel | 0.113 |
| Adds one field of a component to another | Kernel | 0.106 |
| Clamps with `MathF.Min` and `MathF.Max` | Kernel | 0.106 |
| Writes a `float` from a two-float component | Loop over the entities | 0.884 |
| Takes an `Entity` and `Commands` | Loop over the entities | 0.911 |
| The same wrap in an `[EachBlock]` indexed loop | Your loop | 0.589 |
| The same wrap in a named query | `foreach` over rows | 0.772 |

An `[Each]` system measures within 6% of the same value whether or not entities existed when it first ran. The named query does not. When its system first ran while no entity matched, the same `foreach` took 1.18 ns per entity, because the runtime had compiled the loop before the loop ever ran. The [11 November round](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/system-overhead.md) measured that case again at 0.98 ns.

## What a system costs before it does work

A schedule pays a fixed cost for every system it runs, whatever the system does. These cases were measured on 11 November 2026 on the AMD Ryzen AI 9 HX 370 machine, with the process pinned to two cores, .NET 11.0.0-rc.3, one worker, and schedules of 256 systems. Each system visits 16 entities and adds one `double` to another, so almost all of the time is the fixed cost. Each value is the median of five process runs. The [report](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/system-overhead.md) has the ranges, a second machine, and the method.

| System | ns per system per run |
| --- | ---: |
| An empty system that shares its batch with others | 12.6 |
| An empty system in a batch of its own | 10.8 |
| `[Each]` | 24.3 |
| Named query, `foreach` over rows | 26.7 |
| `[Each]` that declares `Commands` | 47.1 |

The named-query system ran near 24 ns in some processes and near 27 ns in others.

The cost per system stays close to these values at any schedule size. The first three rows measured within 4% of them at 16 systems and at 1,024, and the named query within 7%. The last one cost 46.0 ns at 16 systems and 50.5 ns at 1,024.

A query also pays for each archetype it matches. Over 256 entities spread across 64 archetypes of four rows, an `[Each]` system cost 479 ns per run and a named-query system 450 ns, about 7 ns per archetype.

A build without a profile pays more, because the compiler inlines less. As a NativeAOT image on the AMD Ryzen 9 5950X machine in normal use, the `[Each]` system cost 58.9 ns and an empty system in a batch of its own 17.2 ns.

## Parallel execution

Partitioned `[Each]` and `[EachBlock]` systems split each table into row ranges across workers. Named queries run on one thread.

| Entities | Workers | `[EachBlock]`, indexed loop µs | `[EachBlock]`, `Vector256` µs |
| ---: | ---: | ---: | ---: |
| 1,000 | 1 | 0.946 [0.936, 0.950] | 0.227 [0.224, 0.236] |
| 1,000 | 4 | 14.83 [14.75, 15.12] | 14.15 [13.91, 14.38] |
| 100,000 | 1 | 82.82 [82.38, 84.48] | 20.94 [20.93, 21.74] |
| 100,000 | 4 | 44.86 [44.42, 46.31] | 22.62 [22.53, 22.97] |

The table leaves out `[Each]`, because the checkpoint measured it before SIMD kernels. On 5 November 2026, with kernels and the dispatch changes described below, two batches measured `[Each]` with one worker at 0.237 and 0.305 µs for 1,000 entities, and at 21.41 and 22.04 µs for 100,000. With four workers they measured 0.923 and 1.089 µs for 1,000 entities, and 11.96 and 8.549 µs for 100,000.

In this checkpoint, at 1,000 entities, a four-worker update spent 14 to 16 µs, almost all of it dispatching work to the worker pool. The later dispatch change avoids waking workers for a single work item; it adds no row-count threshold for partitioned systems. With workers that spin between batches, the [5 November report](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/performance-hill-climb-report.md) measured the same four-worker update at about 1.5 µs when updates run back to back, and about 32 µs when the calling thread sleeps 2 ms between updates. Measure small worlds with one worker before enabling parallel execution. At 1,000,000 entities, four-worker times varied between processes by more than 100 µs. The [results](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/results.md#movement-by-size-and-worker-count) list them.

## Entity operations

Each case performs the operation once for every entity. For spawn and despawn, every measurement starts from a new world.

| Operation | 1,000 entities µs | 100,000 entities µs |
| --- | ---: | ---: |
| `Spawn` of a two-component bundle | 27.25 [26.99, 28.15] | 3,804 [3,693, 3,999] |
| `SpawnBatch` of the same bundles | 15.25 [15.15, 15.30] | 2,150 [2,133, 2,151] |
| `Despawn`, in shuffled order | 24.70 [24.56, 24.77] | 5,798 [5,607, 6,009] |
| `Get<T>`, in shuffled order | 5.731 [5.728, 5.825] | 1,669 [1,437, 2,967] |
| Insert, then remove a tag | 87.00 [86.32, 89.90] | 8,776 [8,635, 8,811] |
| Insert, then remove a 256-byte component | 95.93 [93.02, 96.03] | 9,571 [9,438, 9,609] |

At 100,000 entities, `Despawn` and `Get<T>` vary by process. A process of a slow kind took 4.4 to 6.0 ms to despawn, and a fast one about 3.5 ms. `Get<T>` took 1.44 to 1.67 ms in most processes and about 3 ms in a few. Spawning grows the entity directory and table storage, so it allocates. `SpawnBatch` reserves storage for the whole batch first.

## Change filters

| Case | 1,000 entities µs | 100,000 entities µs |
| --- | ---: | ---: |
| Write a tracked component on every entity | 0.327 [0.326, 0.445] | 35.39 [29.49, 37.26] |
| `Changed<T>` scan with nothing changed | 0.164 [0.161, 0.164] | 0.169 [0.163, 0.195] |
| Write everything, then a `Changed<T>` scan | 1.427 [1.268, 1.747] | 137.0 [103.0, 141.5] |
| Write one of 16 archetypes, then a `Changed<T>` scan | 0.616 [0.615, 0.634] | 10.88 [10.87, 11.02] |

A `Changed<T>` scan with nothing changed takes about 0.16 µs at both sizes, because it [skips every archetype](/guides/change-tracking#skipping-unchanged-archetypes) without reading a row. The two rows that write every entity are from 5 November 2026. Another batch that day measured the tracked write at 31.02 µs and the write-then-scan case at 126.1 µs at 100,000 entities.

## Things that cost

- Every system costs 10 to 25 ns per run before it visits an entity, and about 50 ns when it declares `Commands`. A query costs about 7 ns for each archetype it matches. [What a system costs before it does work](#what-a-system-costs-before-it-does-work) lists the cases.
- Structural churn moves rows between archetypes. An idle tag insert and remove costs about 87 ns per entity at 1,000 entities.
- Small workloads can cost more to dispatch in parallel than to run serially, as the parallel table shows.
- Workers spin for up to 50 µs after each parallel batch, so frequent small batches keep extra cores busy. A parallel batch that follows a single-item batch wakes blocked workers, which costs about as much as the dispatch in the parallel table.
- A named query whose system first ran while no entity matched keeps a slower loop for the life of the process, 1.18 against 0.77 ns per entity in [one measurement](#each-methods-by-shape). `[Each]` and `[EachBlock]` do not.
- Writable access stamps a change on [tracked components](/guides/change-tracking) even when the value is equal.
- `Added<T>` and `Changed<T>` filters skip archetypes with no stamp since the system last ran, but read every row of an archetype that has one. Changes spread thinly across many archetypes cost more to scan than the same changes kept in a few.
- The first command playback without preallocated command capacity allocated 160.12 KB for 1,000 tag round trips. With 65,536 initial command bytes, it allocated 232 B.

## Reproduce

```powershell
dotnet run --project benchmarks/Archevolt.Benchmarks -c Release -- --quick
./scripts/baseline.ps1
./scripts/baseline.ps1 -IncludeBevy
./scripts/measure.ps1 -Mode All
```

`--quick` runs a short movement measurement in one process. `baseline.ps1` runs the BenchmarkDotNet baseline cases with three process runs and writes their medians and ranges to `artifacts/baseline/`. `-IncludeBevy` also runs the Bevy counterparts, and `-Classes` selects other benchmark classes.

`measure.ps1 -Mode All` runs the workload matrix, single-item cases, partition comparison, BenchmarkDotNet comparison, and JIT disassembly. Use `-Mode Matrix`, `SingleItem`, `Partition`, `Bdn`, or `Disassembly` to run one measurement. The script fails if any command fails or BenchmarkDotNet does not execute all comparison cases.

`-Mode Partition -Runs 3` compares direct and partitioned queries across row counts and checks warmed managed allocations. Add `-BaselineAssembly <path>` to compare against a preserved benchmark assembly with the same benchmark code. `-RuntimeDefaults` uses default runtime compilation settings for the partition comparison. `-Output <directory>` selects where the script saves its evidence.

`SingleItem` measures ten cases in the current build, including no-op and action singletons, generated queries, and partitioned controls. It launches three processes sequentially per case with tiered compilation and ReadyToRun disabled. Each process validates its workload before and after timing and records all pilot, warmup, and measured samples in raw JSON.

Each run creates `artifacts/performance/single-item/<UTC timestamp>/` with the raw JSON, logs, source hashes, Git revision, and environment metadata. Its `summary.csv` uses the baseline-compatible columns `Harness,Case,Runs,MedianUs,MinUs,MaxUs`. The timings are the median, minimum, and maximum of the three process means in microseconds. Compare saved runs with `./scripts/compare-baselines.ps1 -Before <before-directory> -After <after-directory>`.

This mode measures the current build. The [historical single-item report](https://github.com/Stephanvs/archevolt/blob/main/benchmarks/single-item-batches.md) describes a separate experiment with frozen baseline and candidate builds, source swapping, and six launches per variant in ABBA order.

The [v1 performance report](https://github.com/Stephanvs/archevolt/blob/main/.audit/performance-final.md) records the workload matrix, generated code sizes, and JIT and AOT inspection from before table storage and .NET 11. Its numbers are not comparable with the tables above.
